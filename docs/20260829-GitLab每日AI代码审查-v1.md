# 需求三 · GitLab 每日 AI 代码审查 方案

- 版本：v1（修订 1）
- 日期：2026-08-29
- 状态：待评审
- 优先级：**P2（第三个落地）**
- 修订说明：①数据层改为**统一 SQLite**（与 P1 登录共用 `data/console.db`，标准库 `sqlite3`，仍零依赖）；②新增**报告推送**：审查报告生成后按配置推送至用户云服务器接口，便于在自有系统展示。

---

## 1. 背景与动机

公司多个项目由 GitLab 管理。目标是：在总控台配置这些项目的 git 仓库地址，**每日固定时间（默认凌晨 03:00）** 拉取配置内全部项目**当日（昨日）提交**的变更，用 AI 做代码审查（安全 / 性能 / 功能概述），生成报告；每天早上在总控台内查看昨日各项目的提交概况、是否存在性能/安全问题、以及本次提交主要解决了什么功能。

## 2. 现状能力盘点（关键约束：项目坚持**运行时零依赖**）

| 需要的能力 | 现状 | 说明 |
|---|---|---|
| 执行 git 命令 | ✅ `run_cmd`（[server.py](file:///d:/00-code/local-ops/server.py#L695)）| 子进程执行并返回 stdout，状态下沉不抛给上层；git 走系统命令 |
| 调用外部 HTTP（AI / GitLab API） | ✅ `http_get`（标准库 urllib）| 无需引入 `requests`/`openai`，可直连 OpenAI 兼容 API / 公司网关 |
| 后台周期任务 | ⚠️ 仅守护线程模式（`start_log_maintenance`，[server.py](file:///d:/00-code/local-ops/server.py#L3308)）| 可仿照扩展「每日任务调度线程」 |
| 配置持久化 | ✅ `config.json`（[Config 类](file:///d:/00-code/local-ops/server.py#L468)）+ 新增 `sqlite3`（标准库）| 运行配置仍存 JSON；**项目清单、审查报告、推送记录统一入 SQLite** |
| 平台差异 | ✅ 三平台均适配 | git 为跨平台通用，无需额外分支 |
| AI 客户端 + 定时 | ❌ 无 | 用标准库实现，不破坏零依赖铁律 |

## 3. 目标流程

```
[配置] 项目仓库地址 + 认证(可选) + 分支 → SQLite
   │
[每日 03:00 调度]
   │
  1. 逐项目 git fetch/pull/clone
  2. 计算"当日/上次运行以来"提交范围 → git log
  3. 提取提交 diff（安全 / 性能 / 功能分析的输入）
  4. 按项目聚合 → 调 AI(OpenAI 兼容) 审查
  5. 生成报告 → 入 SQLite（项目报告 + 每日汇总）
  6. 按配置推送报告至云服务器接口 → 记录推送状态（成功/失败，失败可重试）
   │
[早上] 总控台「每日代码审查」视图查看：昨日提交概况 + 问题点 + 功能摘要；
      自有系统经云端接口接收报告并展示
```

## 4. 功能拆解

### 4.1 项目配置（GitLab 仓库清单）
- 新增接口 `POST /api/review/projects` 增删改查，字段示例：
  ```json
  { "name": "order-api",
    "remote": "https://gitlab.example.com/team/order-api.git",
    "auth": {"type": "token"|"ssh", "token": ""}, "branch": "main", "enabled": true }
  ```
- 认证：优先复用本机 SSH key（不落库）；仅必须走 HTTPS 且无法用 SSH 的项目才存 Personal Access Token，写入 0600 配置。
- 存储：项目清单入 `data/console.db` 的 `projects` 表（标准库 `sqlite3`，零依赖），替代 JSON 便于检索/对账。

### 4.2 每日定时调度
- 默认 `03:00`，可配置；**跨重启持久**（写配置），启动时检查「今天是否已跑」补偿漏跑。
- 可选加锁防并发重复执行；失败记录并可在页面手动触发补跑。

### 4.3 获取当日提交与变更
- 首选 `git log --since="<昨日零点>" --pretty=... --author=...`；
- changes 输入用 `git show <sha> --format= -- <files>` 或 `git diff parent..sha` 取补丁；
- 处理：首次全量 clone vs 已存在本地仓库增量 fetch；大 diff 截断策略（AI 请求体上限）。

### 4.4 AI 审查
- 用 `run_cmd`/`http_get` 对接 OpenAI 兼容 Chat Completions（公司网关/代理皆可），**不新增 Python 依赖**。
- 输出结构化 JSON 便于渲染与对账：
  ```json
  { "commit": "abc123", "files": ["..."], "summary": "解决了 xxx 功能",
    "security": ["..."], "performance": ["..."] }
  ```
- 失败重试 + 速率控制 + 单次超时保护（沿用现有 `http_get` 超时习惯）。

### 4.5 报告与查看
- 报告入 SQLite（`reports` 表：项目报告结构化 JSON + 每日汇总），权限 `0600`、不进 Git；不再依赖 Markdown 文件（如需导出另加）。
- 总控台新增「每日代码审查」视图：顶部每日汇总卡片（项目数 / 提交数 / 安全警告数 / 性能问题数），下方按项目列出提交与审查结论，可展开 diff 与问题点。
- 可复用现有系统通知提醒「今日报告已就绪」。

### 4.6 报告推送（云服务器展示）
- 配置「推送端点」：`push.endpoint`（云服务器 HTTP 接口 URL）+ `push.token`（如需要）。
- 流程：每日报告写入 SQLite 后，按配置 `POST` 到端点（`http_post`，标准库 urllib）：
  - 请求体为该日汇总 JSON（含各项目报告）；
  - 推送结果入 `push_logs` 表（时间 / 目标 / 状态 `pending|success|failed` / 响应码 / 摘要），供对账与 UI 展示；
  - 失败自动保留并可手动/定时重试 `pending`/`failed` 记录。
- 目标端不归本总控台管理——接口契约（请求体结构、鉴权头）作为配置项交付，字段可扩展。

## 5. 数据结构（config.json 运行配置 + SQLite 数据）

`config.json` 只存调度与连接类运行配置：

```jsonc
"review": {
  "schedule": { "cron": "0 3 * * *", "enabled": true },  // 简化：小时/分钟/每周几
  "ai": { "baseUrl": "https://<company-llm-gateway>/v1", "model": "...",
          "apiKeyEnv": "REVIEW_AI_KEY" },                // Key 走环境变量，不落库
  "push": { "endpoint": "https://<cloud>/api/reports", "tokenEnv": "REVIEW_PUSH_TOKEN" }
  // projects 移入 SQLite
}
```

项目清单与报告统一入 `data/console.db`（标准库 `sqlite3`）：

```sql
projects  -- GitLab 仓库清单
  id INTEGER PK, name TEXT, remote TEXT, auth_type TEXT, auth_token TEXT,
  branch TEXT, enabled INTEGER, last_ran_at TEXT

reports   -- 审查报告（结构化 JSON，可检索）
  id INTEGER PK, day TEXT(YYYY-MM-DD), project_id INT FK, commits_json TEXT,
  findings_json TEXT, created_at TEXT

summary   -- 每日汇总（各项目之上的一览）
  id INTEGER PK, day TEXT UNIQUE, summary_json TEXT, generated_at TEXT

push_logs -- 推送对账（目标云服务器）
  id INTEGER PK, day TEXT, endpoint TEXT, status TEXT(pending|success|failed),
  http_code INT, payload_summary TEXT, attempted_at TEXT, next_attempt_at TEXT
```

## 6. 决策点

1. **定时实现位置**：
   - 方案 A【推荐】后端守护线程自调度 + 配置持久 + 启动补偿，零依赖，随总控台存活；停机则当次漏跑（可补跑/手动触发）。
   - 方案 B：系统定时（launchd / systemd timer / Windows 计划任务），独立存活但三平台维护成本高。
2. **数据层**：统一标准库 `sqlite3`（`data/console.db`），项目清单 / 审查报告 / 每日汇总 / 推送对账全部入库；`config.json` 仅存运行配置。报告文件导出（Markdown）作为可选增强，不入主链路。
3. **AI 凭证**：`REVIEW_AI_KEY` 环境变量（推荐，不落盘）或 0600 配置。
4. **审查粒度**：建议**按项目聚合**当日 diff 一次性审查（省调用次数与成本），报告内再下钻到 commit；大仓库可再按 commit 分批。
5. **认证**：默认本机 SSH；仅必须 HTTPS 且不能用 SSH 的项目才存 token。
6. **推送**：`push_logs` 状态机自动重试；是否暴露「手动重推」入口与失败通知，落地时随 UI 一并确定。

## 7. 优先级与分阶段落地

建议分期：
- **Milestone 1（最小可用闭环）**：SQLite 初始化 + 项目配置（`projects` 表）+「立即运行一次」手动触发 + AI 审查（可先固定一个项目）+ 查看当天报告。
- **Milestone 2**：每日定时调度 + 漏跑补偿 + 汇总视图 + 通知提醒 + **报告推送（`push_logs` + 重试）**。
- **Milestone 3**：多项目并发、分批审查、报告导出（Markdown/检索）、配置项完善。

## 8. 风险与安全（对齐项目既有约定）

- **零依赖红线**：AI 只能走标准库 `urllib`；git 依赖系统命令；不引入 `requests`/`openai`；数据库用标准库 `sqlite3`。
- **安全边界**：能执行 git / 访问仓库属高权限操作；AI 请求与报告可能含代码，**只发往用户配置的 AI 网关 / 推送端点**，不得上传不受信任网络；推送目标必须用户显式配置且视为受信任；报告/日志按 `0600/0700` 收紧、不进 Git；数据库文件 `0600`，敏感 token 走环境变量。
- **新增代码同时更新** `make check` 相关检查与测试（项目要求测试数为 0 即失败）。

## 9. 验收标准

- 配置 1~N 个 GitLab 项目后可在页面手动触发一次，成功产出当日报告并入 `data/console.db`，可在「每日代码审查」视图查看。
- 到达配置的定时时间自动运行；总控台重启后今天仍会补跑（或按配置补偿）。
- 报告正确展示项目/提交数、安全与性能问题、功能摘要；失败有明确原因与补跑入口。
- 配置推送端点后，报告生成即尝试 `POST` 至云服务器，`push_logs` 正确记录状态；失败保留可重试。
- `make check` 全绿；补后端调度/审查/推送相关测试与必要的安全检查。
